1. Purpose and Scope
The application is a custom competition platform for a two-round team coding event in which first-year members choose the priority order of coding problems while senior members solve the problem allocated to their team. The platform manages the complete event lifecycle: team login, temporary credentials, problem reveal, priority submission, deterministic allocation, coding, code execution, scoring, monitoring, anti-malpractice evidence, and final leaderboard.
The application is intentionally designed to avoid a traditional blind auction. Teams do not bid virtual money, and no complex power-up economy is required. Instead, the competitive element comes from strategic problem prioritization and first-come-first-served allocation subject to dynamically calculated problem capacity.

3. Functional Requirements
3.1 Event Lifecycle
WAITING   ↓PRIORITY_SELECTION   ↓ALLOCATION   ↓CODING   ↓ROUND_ENDED   ↓SCOREBOARD   ↓Next Round / FINAL LEADERBOARD
The backend is the authoritative source of event state.
Clients receive state changes through REST APIs and Socket.IO.
A participant must never be able to advance the event state from the browser.
Round timers must be based on server timestamps, not client clocks.
The administrator can start, pause where supported, close, and finalize stages.
3.2 Team and Participant Management
Create/import teams before the event.
Store team ID, team name and member role information.
Associate two login identities with each team: FIRST_YEAR and SENIOR.
Support multiple participants sharing the role identity, subject to configurable simultaneous-session limits.
Recommended maximum active sessions: 2 first-year sessions and 3 senior sessions per team.
Allow administrator to force logout a session.
Maintain audit records for login, logout, password issue and password consumption.
3.3 Temporary Password System
Passwords are temporary session credentials rather than permanent participant passwords.
REQUEST PASSWORD      ↓ADMIN LOGIN REQUEST QUEUE      ↓ADMIN CLICKS "ISSUE PASSWORD"      ↓CRYPTOGRAPHIC RANDOM PASSWORD GENERATED      ↓HASH STORED IN DATABASE      ↓ADMIN COMMUNICATES PASSWORD      ↓PARTICIPANT LOGS IN      ↓PASSWORD MARKED USED / INVALID      ↓SESSION CREATED
Participant selects Team ID and role and requests a password.
Request appears in the administrator Password Manager.
Administrator explicitly approves and issues the password.
Password should be generated using a cryptographically secure random generator.
Suggested format: K7QX-94MP.
Password expires after approximately 5–10 minutes if unused.
Password is single-use.
Plaintext password must never be stored in the database.
Store a strong password hash such as Argon2id or bcrypt.
Rate-limit password requests.
Optionally require an event PIN before allowing a password request.
A new password is required after logout if the participant needs to log in again.
3.4 Login and Role Authorization
Role
Permissions
FIRST_YEAR
Request/login; submit priorities during priority phase; view team status, allocation and score; monitor coding; no code editing or submission.
SENIOR
Request/login; view waiting state during priority phase; edit allocated problem code; run/submit code during coding; view team score.
ADMIN
Full event control, teams, credentials, problems, allocation, submissions, violations, scoring, sessions and leaderboard.
Authorization must be enforced by the backend, not merely by hiding frontend buttons.
Every protected API must validate authenticated session, team, role and event state.
A senior cannot submit to another team's problem by modifying an HTTP request.
A first-year cannot call the submission endpoint successfully even if they manually construct a request.
4. Priority Selection and Allocation Engine
4.1 Priority UI Requirements
Display all five problems with problem number, title, difficulty and concise statement/summary.
Do not expose hidden test cases.
Provide five ranking positions: 1st, 2nd, 3rd, 4th, 5th.
The user must rank all five problems before submission.
Prevent duplicate selections.
Allow reorder using drag-and-drop or numbered selectors.
Display the remaining priority-selection timer.
Display team ID and current team score.
Do not show remaining problem capacity.
4.2 Capacity Calculation
The capacity must be derived from the total number of participating teams. With T teams and five problem buckets, distribute teams as evenly as possible.
baseCapacity = floor(T / 5)remainder = T % 5First 'remainder' problems:    capacity = baseCapacity + 1Remaining problems:    capacity = baseCapacity
Example: for 32 teams, capacities can be 7, 7, 6, 6, 6. The distribution must be deterministic and documented before the round starts.
4.3 Allocation Algorithm
for team in teams_sorted_by_priority_submission_time:    for preference in team.preferences:        if problem[preference].remaining_capacity > 0:            assign(team, preference)            problem[preference].remaining_capacity -= 1            breakif no preference has capacity:    mark team as ALLOCATION_EXCEPTION    notify administrator
Submission timestamp is the primary ordering mechanism.
The server assigns a sequence number when the priority form is accepted.
The same sequence number/order must be used consistently during allocation.
Allocation results are persisted before participants are notified.
An administrator may have a controlled allocation override with an audit log.
5. Round 1 Requirements
Administrator reveals five Round 1 problems.
First-year participants receive the priority-selection interface.
Senior participants see the waiting screen.
Each team submits a complete five-problem ranking.
Priority submission closes when the timer expires or the administrator closes the phase.
Backend allocates problems using capacity and submission order.
All participants receive their team's allocation.
Senior participants receive the coding interface.
First-year participants receive the monitoring interface.
Coding runs for exactly 10 minutes according to server time.
Round score is calculated and shown.
6. Round 2 Requirements
Reveal five new Round 2 problems.
Repeat the complete priority-selection process.
Calculate capacities again from the number of active participating teams.
Allocate using the same deterministic algorithm.
Senior participants receive the Round 2 coding interface.
First-year participants receive the Round 2 monitoring interface.
Coding runs for exactly 30 minutes.
Calculate Round 2 score.
Add Round 2 score to the accumulated coding score.
Combine with the separately maintained first-year aptitude score according to the event's published scoring scheme.

8. Code Execution and Judging
The backend, not the browser, submits code to the judge.
Recommended judge: Judge0 or an equivalent isolated code execution service.
Store hidden test cases on the server side.
Never send hidden test input/output to the participant browser.
Validate team, role, round, allocation and coding window before judging.
Record judge submission ID, language, timestamp, status and test results.
Apply event-specific scoring after judge execution.
Support compile errors, runtime errors, time-limit failures and wrong answers.
Apply CPU/memory/time restrictions through the judge.
Prevent arbitrary server-side code execution outside the isolated judge.
9. Scoring Requirements
For a coding problem, let M be the number of test cases passed. Let W be the problem's difficulty weight.
Problem Score = M × W
Difficulty weights must be configurable by the administrator.
Example: Easy = 1, Medium = 2, Hard = 3.
Round 2 may use a different weight range if the event committee chooses.
Store raw test-case count and weighted score separately.
Total coding score = Round 1 score + Round 2 score.
First-year aptitude score is maintained separately and added according to the published competition formula.
Score changes after finalization require administrator authorization and audit logging.
10. Anti-Cheating and Malpractice Requirements
No software system can absolutely prevent malpractice if participants have unrestricted personal devices and internet access. The platform therefore uses layered controls and produces evidence for administrator review.
Prefer organizer-controlled laboratory computers.
Restrict external internet access during coding where venue infrastructure permits.
Allow only the contest platform and required judge/backend services where practical.
Do not allow source-file upload or ZIP upload as a substitute for the editor.
Record fullscreen exits.
Record browser tab visibility changes.
Record focus/blur events.
Optionally record copy/paste events.
Record submission history and timing.
Record unusual activity as flags rather than automatically declaring guilt.
Run post-event code similarity analysis between teams.
Use token normalization or AST-based similarity rather than only exact text comparison.
Do not use unreliable AI-code detectors as the sole basis for disqualification.
Publish malpractice rules before the event.
If personal devices are allowed, acknowledge that unrestricted AI/search access cannot realistically be prevented.

19. Security Requirements
Use HTTPS in production.
Use secure, HTTP-only session cookies.
Use SameSite cookie protection appropriate to deployment.
Implement CSRF protection where session architecture requires it.
Validate all API inputs server-side.
Use parameterized SQL/ORM queries.
Rate-limit authentication and password-request endpoints.
Never expose password hashes or secrets through APIs.
Never expose hidden test cases.
Use server-side authorization for every protected action.
Sanitize problem statements if rich text/HTML is supported.
Limit request body size and submission source-code size.
Audit administrator actions.
Use isolated execution for submitted code.
Do not place cloud/database/judge secrets in frontend code.
20. Session and Recovery Requirements
Coding state must be independent from browser login state.
Autosave source code approximately every five seconds and/or on significant edits.
If a senior logs out or loses connection, the code remains stored server-side.
A newly authenticated senior from the same team can restore the saved code.
The authoritative timer continues on the server.
Reconnecting clients receive the current event state immediately.
A closed coding phase must reject submissions even if a participant's browser still displays the editor.
21. Monitoring and Audit
Record priority submission timestamp and sequence number.
Record allocation decision and selected priority rank.
Record every code submission.
Record judge result.
Record login/logout events.
Record temporary credential issuance and use.
Record fullscreen/focus/tab events where enabled.
Record administrator overrides.
Record score changes.
Provide an exportable event audit report.

23. Error Handling
If priority submission fails, show an explicit error and preserve entered selections.
If allocation fails, freeze participant transition and alert administrator.
If Judge0 is unavailable, preserve the submission and show a pending state.
If code compilation fails, display the compiler result without losing source code.
If the browser disconnects, preserve server-side timer and autosaved code.
If a password expires, require a new request.
If all five choices are unexpectedly full, create an allocation exception for administrator resolution.
Do not allow duplicate allocation for the same team and round.
24. Problem Management Requirements
Admin can create, edit, publish and retire problems.
Each problem belongs to one round.
Each problem has title, statement, constraints, examples, difficulty and weight.
Hidden tests are maintained separately from the public statement.
Admin can configure time and memory limits.
Problems should be validated before publishing.
Published problem content should not change during an active round unless an emergency administrator override is logged.

28. Acceptance Criteria
A team can request and receive a temporary role-specific credential only through the administrator workflow.
A used or expired temporary password cannot be reused.
First-year participants can rank exactly five distinct problems.
A priority submission receives a server-generated sequence number.
Allocation never exceeds configured problem capacity.
Allocation follows the stored priority ranking and submission order.
The senior role sees exactly the allocated problem.
The first-year role cannot access the code editor or submission endpoint.
The coding timer is server-authoritative.
Code remains available after logout/relogin.
Hidden tests are never returned to the browser.
Judge results are persisted.
Round scores are calculated consistently.
Admin can monitor teams, submissions, sessions and flags.
Final leaderboard is generated from persisted scores.
Critical event actions are auditable.

Test submissions immediately before and after round close.
Test allocation exceptions.
Test administrator overrides and audit logs.
Test code similarity reporting.
Load-test concurrent submissions and realtime updates before the live event.
31. Final Product Definition
The completed system should feel like a purpose-built competitive programming platform rather than a collection of separate pages. The participant experience should be minimal and fast: authenticate, select priorities, receive an allocation, solve or monitor the assigned problem, and view the score. The administrator experience should provide complete operational control without requiring direct database manipulation.
The key architectural principle is that the browser is a presentation and interaction layer, while the backend is the authority for event state, allocation, timing, permissions, scoring and submission validation. This prevents participants from manipulating the competition by modifying frontend code or API requests.
For the first production version, the recommended scope is React + TypeScript, Node.js + Express, PostgreSQL, Socket.IO, Monaco Editor and Judge0, with a dedicated administrator dashboard and server-side session/authentication system.
